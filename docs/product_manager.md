# Touchline Product Management Strategy & Handoff Document

## Executive Product Mandate

Touchline is a browser-based, asynchronous, persistent multiplayer football-management universe. The product prioritizes social competition, persistent consequences, explainable systems, meaningful financial trade-offs, and enduring world history.

The primary product thesis is:
> **Every club has a personality. Every player has a story. Every decision has consequences.**

The MVP core validation question (PRD §85) is:
> **"Is managing a club in a world populated by other real managers more compelling than managing a club alone?"**

The PRD (`docs/Touchline — Persistent Multiplayer Football Manager PRD.md`) and Technical Plan (`docs/Touchline_Technical_Implementation_Plan.md`) serve as the authoritative sources of truth. `OPENCODE.md` records resolved architectural decisions and domain invariants. This document acts as the product strategy manifest, sprint breakdown directory, open-decision registry, and team handoff guide.

---

## Delivery Posture & Technical Invariants

- **Strict Phasing:** Ship scope strictly according to the task manifests in `docs/tasks/`. Do not pull V1+ features into Phase 1 MVP merely because schema hooks exist.
- **Server Authority:** The server is the sole source of truth. The Nuxt 3 client renders state and submits commands; it never simulates outcomes (OPENCODE.md, Tech Plan §1).
- **Append-Only Ledger:** Financial balance is strictly `SUM(ledger_entries)`. No stored `balance` column exists in `finance` tables (OPENCODE.md, Tech Plan §6).
- **Event Spine:** All state changes emit typed `world.events` carrying `world_id`, tick counters, actor IDs, causal chains (`CausedBy`), and typed JSON payloads (Tech Plan §4).
- **Explainability:** All scored outcomes (board confidence, transfer desire, job security) return `Explanation` objects with explicit factor breakdowns (Tech Plan §8).
- **Relationship Graph:** Modeling entity relationships as polymorphic graph edges in `social.relationships` (`player`, `manager`, `club`) (Tech Plan §6).
- **Unified PolicyBot Execution:** Absence delegation and AI-controlled clubs invoke the exact same command handlers a human manager calls (Tech Plan §10).
- **Competitive Fairness:** Strict non-pay-to-win policy. Real-money purchases cannot grant competitive or financial simulation advantages (PRD §78).

| **OPD-16** (world lifecycle + manager→club assignment boundary, S02-02) | **(1) Worlds and clubs are created by an admin at game start:** world lifecycle is an admin-only HTTP surface (`POST /api/admin/worlds` to provision, `POST /api/admin/worlds/:id/status` to launch/pause/resume/archive). | **OPD-17** (configurable world clock, S02-03) | **(1) The world clock is a dedicated scheduler binary driven by runtime config.** The scheduler reads each playable world's cadence strings from `world.world_config` (`tick.*_cadence`, cron 5-field specs) and fires `WORLD_TICK` events over the event bus. The spec set the clock drives is `hourly|daily|weekly|monthly|seasonal` per plan §5 — cadence *values* live in the DB, never in code; changing a value (admin `POST /api/admin/worlds/:id/config`) takes effect on the next sync, **no redeploy**. **(2) Match ticks are NOT world-cron.** `tick.match_cadence` is seeded but ignored by the world clock: plan §5 hands live match ticks to per-match goroutines in the match engine (S04). The plan's economic/social(daily-adjacent), training/daily, league/weekly, financial/monthly, and seasonal passes map to `hourly|daily|weekly|monthly|seasonal` respectively. **(3) Ticks are world-scoped and monotonic.** Only `active`/`open_beta` worlds tick; each emission advances that world's `current_tick` and is written to `world.events` with payload `{"granularity":"<g>"}` + actor `system` — subscribers filter by granularity to handle only the cadences they own. Paused worlds stop ticking; resumed worlds resume from the config. **(4) One scheduler leader.** The scheduler holds a Postgres advisory lock (`hashtext('touchline:scheduler')`) for its lifetime, so duplicate scheduler instances cannot double-fire cadences; a second instance waits for leadership. **(5) Soundness on failure.** Fire guards playable status inside the same transaction (`UPDATE … WHERE status IN ('active','open_beta')`), making stale cron entries safe after pause/archive; malformed cron specs are skipped + logged, never fatal. Match-range determinism and ledger-side effects of ticks arrive with the engines that consume them (S03-01, S04, S06). | S02-03 |

| **OPD-18** (world bootstrap, S03-01) | **(1) One admin trigger materializes a whole provisioning world.** `POST /api/admin/worlds/:id/bootstrap` turns an empty `provisioning` world into one AI starter club with a squad in a single transaction: `404` unknown world, `409` if the world is already launched or already has clubs, `503` when the `ref` pools are empty, and `CLUB_CREATED` + `WORLD_BOOTSTRAPPED` events written in the same tx. **(2) First club = AI starter club; humans enter via OPD-16 only.** The bootstrap club is `is_ai_controlled=TRUE` with a policy-bot `manager.managers` row; the only sanctioned path for a human manager to take it is the OPD-16 offer→accept flow (admin `POST /api/admin/offers`). No auto-hire, no direct assignment. **(3) Squad comes from the shared generation subsystem.** `SquadSizeDefault=24` (2 GK / 7 DEF / 7 MID / 6 FWD + 2 flexible outfield), generated by `pkg/playergen` with a collision registry; pools read from `ref.nationalities` + `ref.name_pool` at runtime per OPD-13(1). Ages 17–33; `date_of_birth` anchored to `COALESCE(launched_at, created_at)` so ages are season-consistent. **(4) Seeded for replay.** One int64 seed per world drives the whole squad and is persisted on `WORLD_BOOTSTRAPPED.random_seed`; identical seeds reproduce identical squads. **(5) Reads are world-scoped.** `GET /api/clubs` (caller's world via the manager row, OPD-15(3)) and `GET /api/clubs/:id` (club + policy-bot manager + squad; `404` across worlds) are the S03-01 read surface. Attributes/contracts/finance and squad→depth-chart ownership arrive with S05; competition structure is OPD-01 (S04-01). | S03-01 |
| **OPD-19** (Redis boundary + the single realtime socket, S02-04) | **(1) Redis is an ephemeral transport, never authoritative storage.** S02-04 uses Redis strictly for WebSocket **pub/sub fan-out** (AC1); all authoritative gameplay state stays in Postgres (`world.events` is the replay source). Sessions/rotation remain in `auth.sessions` per OPD-15(5); rate limiting stays deferred to S11/OPD-08. **(2) The browser authenticates the handshake with the existing httpOnly cookie.** `/ws` runs behind `requireAuth` (OPD-15 access token; same-site localhost works), the server checks the browser `Origin` against `APP_ORIGIN` before upgrading (cross-site socket hijack blocked), and the world is derived from the manager row (OPD-15(3)). A cross-site ticket endpoint is documented future work if deployments ever split frontend/API origins. **(3) One socket per session.** Nuxt `useSocket()` is a singleton — screens subscribe by type through Pinia stores (new `stores/realtime`), never open their own sockets (AC3). **(4) Multi-pod fan-out.** All delivery flows through a broker subscription: Redis pub/sub (single channel `touchline:realtime`; events carry `world_id`) so 1..N API pods behave identically, with an in-process `LocalBroker` fallback when `REDIS_URL` is unset/unreachable (bare `go run`; fail-soft, never fatal). Events are world-scoped at delivery — a socket can never observe another world's stream. **(5) Proof event + control protocol (AC5).** The scheduler worker publishes `world_tick {event_id, granularity, tick}` for every `WORLD_TICK`, so browsers watch fire-and-forget live ticks; client `ping`→`pong`, unknown client types answer with a typed `error` envelope, unknown server types are ignored by the client (warn + continue). A missed live push never corrupts state — replay always comes from Postgres. | S02-04 |
| **OPD-20** (competition structure — resolves OPD-01, S04-01) | **(1) Leagues are admin-declared entities per country; the engine infers nothing.** Competition shape (countries, leagues, tiers, team counts, promotion/relegation numbers) is declared up-front via the admin HTTP surface — `POST /api/admin/countries`, `POST /api/admin/leagues`, `PATCH /api/admin/leagues/:id/adjacency` — before `seed-competition` is called. This **resolves OPD-01**: no initial league-size/P&R numbers are baked anywhere; the admin's declared values are exactly what the engine consumes. **(2) Adjacency must be symmetric** (`validateAdjacency`, seed-time only): a league's `promotions` must equal its promoted-to league's `relegations`, any non-zero movement requires a link, and a league with no neighbors must declare zero movement — else `ErrAdjacencyMismatch` at seed time. Leagues may be created before neighboring leagues exist (no create-time link requirement). **(3) Reads are world-scoped and tier-ordered.** Manager reads (`GET /api/competitions`, `/:id`, `/:id/fixtures`, `/:id/standings`) resolve the caller's world from the manager row (OPD-15(3)); the world's starter club always lands in the top tier so a lone manager always has a visible competition. | S04-01 |
| **OPD-21** (live match execution, S04-02) | **Live matches run on per-match real-time goroutines (Tech Plan §5), never on the world clock.** Matches in the fixture range auto-start, tick in real time at a world-config cadence (default ~20s per simulated minute, key `tick.match_cadence` is seeded but the world clock ignores it per OPD-17(2)), accumulate live events, and finish deterministically at full time. Managers can issue **live substitution/tactic changes** that feed ordered live inputs into the running simulation (S05-01 controls; the engine replays `seed + ordered inputs` to the identical outcome). The observer feed is delivered over the S02-04 realtime socket (S04-03). | S04-02 |
| **OPD-22** (seed & rollover contract, S04-01) | **(1) One seed per country, seeded from the bootstrap.** `POST /api/admin/worlds/:id/seed-competition` builds one master `*rand.Rand` from `WORLD_BOOTSTRAPPED.random_seed` (503 `ErrWorldNotBootstrapped` otherwise); every club and fixture derives from it, so identical seeds reproduce identical competitions. A league whose fixtures already exist errors `409 ErrLeagueAlreadySeeded`; the whole country seeds in a single transaction. **(2) Entry construction.** The starter club (OPD-18) is placed in the selected league; leagues then fill to `team_count` with `GenerateAIClub` clubs using fresh distinct names; all non-starter clubs must be consumed by top tier (else `ErrNoStarterClub`). **(3) Fixture shape.** Full home-and-away double round-robin; `matchday` = round index + 1 (so a two-leg pair per opponent); `scheduled_at` anchored to the bootstrap reference, kickoff 19:00 UTC. **(4) Events.** Per league `SEASON_CREATED` (season_id/label/number, team_count, fixture_count, matchdays) plus one country-wide `COMPETITION_SEEDED` with league summaries. **(5) Rollover cascade.** When the last fixture in a country completes, `maybeCompleteSeason` fires one transaction-per-country `rolloverCountry`: every league's season → `completed`, next entries = stayers + promoted-from-below + relegated-from-above (appended, never overwritten; team counts must reproduce exactly or the tx aborts with an internal error), and next seasons/fixtures schedule from the last-scheduled-day anchor. Emits `SEASON_COMPLETED` (champion), `CLUB_PROMOTED`/`CLUB_RELEGATED` (destination_id), and per-league `SEASON_CREATED` with entries. | S04-01 |
| **OPD-23** (event publication contract — resolves P0 `docs/em/event-delivery-atomicity.md`, S04-04) | **(1) The transactional outbox is the only producer path.** Every event producer records the `world.events` row and enqueues its `touchline_event` River job in the *same* transaction as the business state it describes — via the shared primitive `eventbus.RiverBus.PublishTx(ctx, tx, ev)` (`Publish` becomes `BEGIN → PublishTx → COMMIT`). A committed state change whose event is undispatched is impossible by construction; the event row, its dispatch, and the state are one atomic unit. **(2) No silent fan-out.** A failed event insert/enqueue aborts the enclosing transaction; publish errors always propagate (removes the manager `publish` discard and the competition rollover `_ = recordSeedEvent` discards). **(3) Identity captured at record time.** Producers write with `RETURNING id, occurred_at` into the same `*Event` instance so dispatch and any causal chain (`caused_by_event_id`) reference the persisted ID, and events stamp the real `world.worlds.current_tick` (competition events no longer hardcode `0`). **(4) At-least-once, idempotent, repairable, observable.** Duplicate publishes of one ID dedupe (`ON CONFLICT (id)` + River `ByArgs` unique). A worker repair sweep re-enqueues any committed-but-undispatched row by its original ID (scan for rows lacking a matching `touchline_event` job; `Publish` re-enqueue; safe with N workers) and logs `event_repair_sweep {scanned, repaired, oldest_lag_s}`; the existing river queue-depth metric drives the worker HPA. **(5) Realtime is a consumer, not a producer.** `world.events` stays authoritative and append-only; Redis remains ephemeral fan-out (OPD-19(1)); `world_tick`/`match_tick` envelopes are published by the worker *after* dispatch, not as producer outbox writes. | S04-04 |
| **OPD-24** (world calendar semantics — resolves P0 `docs/em/world-calendar-tick-semantics.md`, S04-04) | **(1) The calendar is a dedicated day counter, not the monotonic tick.** New `world.worlds.current_day` counts in-game days since launch; `worldDate` computes `date = COALESCE(launched_at, created_at) + current_day days`. `current_tick` stays the monotonic ordering/audit counter advanced by *every* granularity (OPD-17(3); form/live reads and `world.events.world_tick` stamping unchanged). **(2) Only the daily emission advances the calendar.** Each `WORLD_TICK{daily}` increments `current_day` by exactly one in the same transaction as the counter; hourly/weekly/monthly/seasonal emissions never touch it. Contract: one daily emission ⇔ one in-game day, so fixture eligibility on the daily handler advances exactly one matchday regardless of the other four schedules; paused worlds don't advance; the day count is the count of daily emissions since launch (repeated emissions simply mean days passing). **(3) Default pacing ≈ 3 in-game days per real day.** Seeded default `tick.daily_cadence` changes to `0 */8 * * *` (00/08/16 UTC); cadence stays runtime-configurable per world (OPD-17(1)) — changing it alters the *rate* the calendar advances, never single-step semantics, and never leaks into other granularities' timing. **(4) Existing worlds.** Migration backfills `current_day` from each world's stored daily `WORLD_TICK` count so already-seeded dev fixtures stay eligible; the new default cadence applies to worlds launched after deploy (config seeds `ON CONFLICT DO NOTHING`, so untouched worlds keep their old rate). | S04-04 |
